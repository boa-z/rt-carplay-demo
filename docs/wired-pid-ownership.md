# Wired receive integrity: final DATA PID ownership

[简体中文](zh-CN/wired-pid-ownership.md)

The November 15 board capture establishes recurring malformed NCM completions while wired CarPlay remains connected: readable five-second windows contain 14–15 signature failures, with receive wake/rearm/parse and synchronous TX maxima around 0–1 ms. The rejected buffers begin with non-NCM bytes, rather than a valid header rejected only for table layout. The screen owner has no intervals above 100 ms in these windows, yet partial-message gaps exceed 500 ms; video reports zero queue drops, decoder errors and resets. This points to receive integrity before the screen socket and makes the former Carrier/EP0 lock chain an inadequate explanation for this capture. It does not establish which USB transactions were lost or whether every visible pause has the same cause.

The maintained EHCI overlay previously read `qh->hw.overlay.token` into `urb->data_toggle` before its existing unlink helper stopped the affected schedule and waited for quiescence. A completed qTD is not an ownership barrier for the controller-cached QH overlay. The unlink helper already invalidates that overlay after quiescence, but its newer value was too late for the PID copied into the URB. Rearming with an old PID can discard the next expected USB packet as a duplicate, leaving an NCM continuation without its header. This is a candidate explanation for the board signature failures; a USB capture or successful controlled image comparison is still required to establish board causality.

The initial candidate moved the existing unlink/byte-accounting call before the overlay snapshot. It copied the refreshed PID after successful unlink; STALL/BABBLE-specific PID resets still ran afterwards. Existing schedule quiescence, cancellation ownership, IAA cohort handling, transfer sizes and NCM validation remained in force. The change belongs to the existing CherryUSB platform patch; upstream CherryUSB and the portable rt-carplay and IPHETH submodules are unchanged. See the later IAA handoff candidate below for the current copy location.

The actual-HCD host regression models separate controller/CPU visibility: a short 1528-byte IN completion consists of three 512/512/504-byte packets, so DATA0 must advance to DATA1, but the final overlay becomes visible only after schedule quiescence. The previous implementation delivers the right byte count with the wrong next PID and fails the assertion; the candidate passes. Existing short/zero/full/error/control chains, STALL toggle reset, cancellation, predecessor cache and IAA cohort cases also pass under ASan/UBSan. This is a modeled interleaving, not a measured controller writeback trace.

For a board comparison, use the same iPhone, USB cable and image settings. After each image connects, run `carplay_perf on`, move or scroll the same screen continuously for at least 60 seconds without music, then repeat with music. Retain complete raw logs and action times. Compare NCM `signature` errors, other receive/network errors, incomplete-screen ages and partial gaps, RX/display cadence, queue drops and decoder resets. Stationary content is not a maximum-FPS workload. Stop aggregate logging with `carplay_perf off`; retain the matching ELF if an exception appears. Also verify reconnect, music and wireless operation. A good host test or cross-build alone does not mean the stutter is fixed.

## Board follow-up and completion trace

After the user reported flashing the PID candidate, serial access through aiburn on port 9100 worked. The board still reported NCM signature failures: one readable 5070 ms window had 17 receive errors, including 14 signature failures, and another 5095 ms window had 14 receive errors, including 13 signature failures. A separate clean status snapshot had RX=41171, rxerr=222, TX errors=0 and USB errors=0, with Carrier and link up. Video status had 1499 frames, zero dropped/errors/resets and average decode/present times of 8/7 ms. The captured monitor backlog interleaves some intervals, and user interaction times were not recorded; these are not controlled FPS comparisons. The PID candidate has not eliminated the observed corruption or established a stutter fix.

The optional `usb_ehci_rxtrace` command collects bounded evidence at successful HCD completion, after unlink/byte accounting and before updating the URB's next PID. It observes only 64 KiB bulk-IN requests. Enable with `usb_ehci_rxtrace on`, reproduce the same moving-screen workload, stop with `usb_ehci_rxtrace off`, then run `usb_ehci_rxtrace` to print the retained summary and last twelve anomalies. It starts disabled, clears evidence on enable, retains evidence on disable, performs no IRQ printing or allocation, and never retains payload buffers or changes PID/recovery policy. While enabled it invalidates only the first cache line of the already unlinked receive buffer and reads at most twelve header bytes. Stop `carplay_perf` separately when finished; leave the serial Monitor running.

`pid_mismatch` compares the overlay's next PID against the starting PID and the parity of received USB packets. A short transfer whose length is an exact multiple of the endpoint maximum packet size includes a terminating zero-length packet; a full request does not. `headers` counts plausible NTH16 headers with matching signature, header/index fields and block length, not fully validated NTBs. `bad_headers` excludes empty completions and four-byte Apple control notifications. `sequence_gaps` counts nonconsecutive plausible NTH16 sequence values on the same bus/address/endpoint, including possible session/device resets; it is not by itself proof of packet loss. Only one active NCM stream is expected for the board's single iPhone session. A mismatch is evidence for further descriptor/PID investigation, not permission to override the PID from a formula.

Invalid NCM prefixes already present in the HCD trace narrow the fault to USB delivery, descriptor processing or DMA visibility before the normal receive callback; they do not identify which of these is responsible. Clean completion headers with later driver signature failures require investigating the completion-to-consumer interval. Correlate this trace with the existing IPHETH and screen-wait summaries before changing transfer framing, parser validation or media behavior. Host regression checks the trace's actual HCD hook, packet parity including ZLP/full-request cases, sequence continuity, control-notification exclusion, disabled mode, length bounds and bounded anomaly storage under ASan/UBSan. Physical validation of the new trace image remains separate.

## IAA handoff candidate after trace capture

The user subsequently reported flashing the completion-trace image. Its shell command was present and successfully enabled. A retained board summary recorded 24766 completed receives, 24585 plausible headers, 181 bad headers, 484 PID parity mismatches and 707 sequence discontinuities. The same session's clean IPHETH status later showed 284 parser errors, with TX/USB errors zero and Carrier/link up; the trace and later lifetime status cover different intervals. Performance windows still contained signature failures and partial-screen waits. The installed IMG hash was not independently read back. These observations locate some malformed headers before the receive callback, but do not prove that the PID snapshot is wrong rather than the byte accounting, or that every visible pause shares one cause.

The next candidate retains the starting URB PID through unlink and reads the final hardware overlay PID in `ehci_urb_waitup`, after the asynchronous QH's existing IAA cohort has completed and before signaling/freeing/calling back. It refreshes the overlay cache at this handoff and updates the PID only on successful completion, preserving error-specific resets. Periodic completion retains its existing immediate callback path. The packet-count formula remains diagnostic only. Existing schedule quiescence and IAA cohort rules are unchanged; no additional IAA round or speculative timing delay is introduced.

The opt-in trace now retains both `unlink` and `deliver` observations, with separate delivered/bad-header/PID-mismatch counters. Both observations see the same starting URB PID before its final update. Compare early and delivery mismatch counts to test whether the later boundary resolves the inconsistency. Each observation reads at most twelve header bytes and invalidates the first payload cache line while the buffer remains owned; no payload pointer is retained. Trace output is split into calls that fit the board's 128-byte console buffer, including newline/NUL. The original long detail line was truncated on the board, so its token/anomaly details are not usable evidence; the short summary above was intact.

An actual-source regression independently models the final overlay PID becoming visible at the later IAA boundary. The preceding unlink-snapshot policy fails with the correct byte count but wrong callback PID, and the handoff policy passes. Host tests also exercise both trace stages and worst-case numeric output within the console bound. This is a modeled interleaving, not measured D213 DMA writeback behavior; the new image still requires board comparison. Linux's maintained [EHCI queue code](https://github.com/torvalds/linux/blob/master/drivers/usb/host/ehci-q.c) illustrates why overlay ownership and controller quirks require care, but its Intel/AMD-specific comments do not establish the D213 cause or justify copying its delays.

## IAA result and short-IN stop correction

The subsequent complete board trace recorded 10481 receives, 140 bad headers, 349 PID mismatches and 571 sequence gaps. The delivery stage had exactly the same 140 bad headers and 349 PID mismatches as the unlink stage. The later PID snapshot therefore did not eliminate the observed corruption. Several retained overlays were still ACTIVE (`40008d80`/`c0008d80`) after software accounted a short receive. Another overlay, `2a009d80`, had only 10752 bytes remaining in a later 16384-byte qTD. These observations support investigating reception beyond the short boundary, rather than assuming the mismatch proves stale PID visibility.

The earlier assumption that an alternate-next terminate bit stops a multi-qTD short IN was incorrect. EHCI can instead follow normal Next when alternate-next is terminated. Linux's queue builder explicitly points IN alternates at an inactive dummy to stop the queue for short-read cleanup. Our previous builder left alternates terminated: later qTDs could consume following NTBs while the software short scanner accounted only through the first short qTD. This explains how receive bytes can disappear from software accounting and why an overlay's PID need not match the reported length. This is a concrete descriptor-path defect and a supported explanation of these logs; its contribution to physical stutter still needs the corrected image comparison.

The correction gives every multi-qTD bulk-IN chain one inactive HALTED stop qTD and points the real data qTDs' alternate links at it. The stop is also linked after the last data qTD so existing cache flush and reclamation traverse it. Completion/accounting skip this software-owned stop rather than reporting a data STALL. Allocation failure reclaims the unpublished chain and returns NOMEM. Single-qTD IN, bulk OUT and control/status chaining are unchanged. The 64 KiB receive allocation remains intact; no media or protocol rewrite is involved. The opt-in trace also reports ACTIVE/HALTED overlay counts at unlink and delivery; a successful real-data completion remains observable even when its overlay references the intentional halted stop.

Actual-source ASan/UBSan regressions model the controller's short-advance decision on descriptors from the real builder, covering all four short positions with zero/nonzero lengths, untouched active tails, full IN/OUT, single IN, control status, resource exhaustion and reclamation. The preceding IAA image's driver fails the new short-advance assertion, while the corrected driver passes. This controller model is not a USB bus capture. Acceptance still requires board header/PID/error/cadence evidence, reconnect, music and wireless checks. The aiburn CLI now preserves logs consumed by its Monitor probe: `readlog` includes them and serial `sendcmd` puts preceding evidence in `monitor_probe_log`, separately from the command reply. Offline functional checks cover both paths; no Monitor stop is introduced.
