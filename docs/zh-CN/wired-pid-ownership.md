# 有线接收完整性：最终 DATA PID 的所有权

[English](../wired-pid-ownership.md)

11 月 15 日实机日志确认：有线 CarPlay 保持连接时，完整可读的五秒统计窗口出现 14–15 次 NCM 签名错误，而 RX 唤醒、重挂、解析和同步 TX 的最大耗时约为 0–1 ms。被拒绝的缓冲区以非 NCM 内容开头，并非仅因为表布局不同而拒绝有效包头。相同窗口没有超过 100 ms 的视频接收主循环间隔，视频半包等待却超过 500 ms；视频队列丢弃、解码错误和重置均为零。这将重点指向屏幕 Socket 之前的数据完整性问题，旧版 Carrier/EP0 锁阻塞链不足以解释本次日志。但这些数据不能单独证明具体丢失了哪些 USB 事务，也不能证明所有可见停顿均来自同一原因。

当前维护的 EHCI 补丁原先在安全摘链之前，将 `qh->hw.overlay.token` 中的 DATA PID 复制到 `urb->data_toggle`；摘链函数随后才停止相关调度并等待静止。qTD 完成并不构成控制器缓存的 QH overlay 的所有权屏障。摘链函数本来会在调度静止后重新失效该 overlay 缓存，但此时已经错过了复制到 URB 的 PID。下一次接收使用旧 PID 时，可能将手机发出的预期 USB 包当作重复包丢掉，留下没有 NCM 包头的后续内容。这是实机签名错误的候选解释，仍需 USB 抓包或受控镜像对照建立实机因果证据。

初版候选修复将现有摘链及字节统计调用移到 overlay 快照之前，在摘链成功后复制 PID，STALL/BABBLE 对 PID 的重置仍在读取之后执行。现有调度静止、取消所有权、IAA 完成批次规则、传输大小和 NCM 校验保持原有策略。修改位于现有 CherryUSB 平台补丁，上游 CherryUSB、可移植 rt-carplay 和 IPHETH 子模块均未改动。当前复制位置见下文后续 IAA 交接候选方案。

真实 HCD 的 Host 回归测试模拟控制器与 CPU 的独立可见性：1528 字节的短 IN 由 512/512/504 三个 USB 包组成，DATA0 应推进为 DATA1，但最终 overlay 仅在调度静止后可见。原实现虽然返回正确长度，却返回错误的下一 PID，断言失败；候选修复通过。ASan/UBSan 下原有短包、零长度、完整传输、错误、控制状态阶段、STALL toggle 重置、取消、前驱缓存及 IAA 批次测试也通过。这是可复现的模型交错，不是对控制器实际写回顺序的测量。

实机对照应保持 iPhone、USB 线及镜像配置一致。每个镜像连接后执行 `carplay_perf on`，不播放音乐，连续移动同一地图或滚动页面至少 60 秒，再播放音乐重复测试；保留完整日志和动作时间。比较 NCM `signature` 错误、其它接收/网络错误、屏幕半包等待、接收与显示节奏、队列丢弃及解码器重置。静止页面不能用作最高帧率测试。结束执行 `carplay_perf off`；发生异常时保留匹配 ELF。还需验证重连、音乐和无线功能。Host 测试或构建成功不能替代实机卡顿修复验收。

## 实机复查及完成阶段诊断

用户报告刷入 PID 候选镜像后，通过 aiburn 的 9100 服务成功读取串口。有线连接仍出现 NCM 签名错误：一个可读的 5070 ms 窗口有 17 次接收错误，其中 14 次签名错误；另一个 5095 ms 窗口有 14 次接收错误，其中 13 次签名错误。独立的清晰状态快照显示 RX=41171、rxerr=222、发送及 USB 错误均为零，Carrier 和链路正常。视频状态为 1499 帧，丢弃、错误及重置均为零，平均解码/显示耗时为 8/7 ms。Monitor 积压日志中部分区间交错，未记录用户操作时间，因此不能据此给出受控帧率对比。PID 候选修复尚未消除观测到的数据异常，也未证明卡顿已修复。

新增按需启用的 `usb_ehci_rxtrace`，在 HCD 成功完成摘链和字节统计后、更新 URB 下一 PID 前采集有界信息，仅观察 64 KiB bulk-IN 请求。执行 `usb_ehci_rxtrace on` 开始采集，连续操作同一页面复现，执行 `usb_ehci_rxtrace off` 停止，再执行 `usb_ehci_rxtrace` 打印保留的统计及最后十二条异常。默认关闭，开启时清空记录，关闭时保留证据；中断内不打印、不分配内存、不保留载荷缓冲区、不更改 PID 或恢复策略。启用期间仅对已经摘链的接收缓冲区首条缓存线做失效处理，最多读取十二字节头部。完成后另行关闭 `carplay_perf`，保持串口 Monitor 运行。

`pid_mismatch` 根据接收前 PID 和实际 USB 包数的奇偶性核对 overlay 下一 PID：短传输长度恰为最大包长整数倍时包含一个结束零长度包，完整请求不额外计入该包。`headers` 仅表示 NTH16 签名、头长度、索引及块长合理，不表示完整 NTB 通过解析校验。`bad_headers` 排除空完成和四字节 Apple 控制通知。`sequence_gaps` 统计同一总线/地址/端点上合理 NTH16 头的序号不连续，也可能受到会话或设备重置影响，不能单独视为丢包证据。本板单 iPhone 会话预期只有一个活动 NCM 流。发现 PID 不一致后应进一步分析描述符，不能直接用计算公式覆盖 PID。

若 HCD 诊断阶段已存在异常 NCM 前缀，可将范围缩至常规接收回调前的 USB 交付、描述符处理或 DMA 可见性，但仍不能据此确定其中哪一项负责；若完成阶段头部正常、驱动后续才发生签名错误，应调查完成到消费之间的交接过程。应结合 IPHETH 和屏幕等待统计继续判断，再决定是否调整传输边界、解析校验或媒体行为。ASan/UBSan 下的 Host 回归覆盖真实 HCD 诊断调用点、零长度结束包及完整请求的包数/PID 计算、序号连续性、控制通知排除、默认关闭、长度边界及有界异常记录。新增诊断镜像的实机验证仍须单独完成。

## 抓取诊断后的 IAA 交接候选方案

用户随后报告刷入接收诊断镜像，串口确认诊断命令存在且成功启用。停止后保留的统计为：24766 次接收完成、24585 次合理头部、181 次异常头部、484 次 PID 奇偶核对不一致、707 次序号不连续。同一会话稍后的清晰 IPHETH 状态有 284 次解析错误，发送及 USB 错误均为零，Carrier/链路正常；诊断区间与后续累计状态区间不同。性能日志仍有签名错误和屏幕半包等待。没有独立读回已安装镜像的哈希。这说明至少部分异常头部在接收回调前已存在，但尚不能确定是 PID 快照错误还是字节统计不一致，也不能证明所有卡顿均由同一原因导致。

后续候选方案在摘链阶段保留 URB 起始 PID，直到异步 QH 所属的现有 IAA 批次完成，在 `ehci_urb_waitup` 发信号、释放或回调之前重新失效 overlay 缓存并读取最终硬件 PID。仅成功完成时更新 PID，错误专属重置保持原逻辑。周期传输保持现有立即回调路径。包数公式仅用于诊断，不覆盖硬件 PID。调度静止及 IAA 批次规则不变，没有增加 IAA 轮数或猜测性的等待延时。

按需诊断现在保留 `unlink` 与 `deliver` 两个阶段，并分别统计交付次数、异常头部及 PID 不一致。两个阶段均在更新 URB PID 前观察同一个起始 PID，可对比摘链与交付阶段的计数，验证延后读取是否消除不一致。每次观察最多读取十二字节头部，并对仍归当前传输所有的缓冲区首条缓存线做失效处理，不保留载荷指针。输出已拆成适配板上 128 字节控制台缓冲区的短调用，包含换行和结束符。初版长明细行在板上被截断，因此 token 和异常明细不能作为有效证据，上述较短汇总完整保留。

真实源码回归独立模拟最终 overlay PID 到较晚 IAA 边界才可见的场景：前一版摘链快照策略虽然字节数正确，但回调 PID 错误；交接策略通过。Host 测试同时覆盖两个诊断阶段及最大数字宽度下的控制台长度。这仍是模型交错，不是 D213 DMA 写回时序的实测，新镜像需要实机对照。[Linux EHCI 队列实现](https://github.com/torvalds/linux/blob/master/drivers/usb/host/ehci-q.c) 可用于研究 overlay 所有权及控制器差异，但其中针对 Intel/AMD 的注释不能证明 D213 根因，也不能作为照搬延时的依据。
# 短包停止链修正的后续证据

后续完整实机记录共 10481 次接收，包含 140 次异常头部、349 次 PID 不一致和 571 次序号不连续；摘链和 IAA 最终交付阶段的异常头部与 PID 不一致计数完全相同。因此，延后读取 PID 并未消除本次实机异常，不能据此宣布卡顿修复。多条短包完成记录的 QH overlay 仍为 ACTIVE（`40008d80`、`c0008d80`），另一条 `2a009d80` 表明后续 16384 字节描述符只剩 10752 字节未接收，需要检查软件短包边界以后的数据是否已被控制器消耗。

此前认为 alternate-next 的 terminate 位能终止多描述符短包接收，这个假设不正确：alternate-next 终止时，EHCI 可以继续沿普通 Next 前进。Linux 的 EHCI 接收链明确使用 inactive dummy 停住短包后的队列。原构建器的 alternate-next 全部终止，后续描述符可能继续接收下一个 NTB，而软件仅统计到第一个短包为止，造成交付数据缺失和 PID 与交付长度不一致。这是可以复现的描述符路径缺陷；它对实机卡顿的实际影响仍须刷入修正镜像后对照确认。

修正为每条多描述符 bulk-IN 链分配一个 inactive HALTED 停止描述符，所有真实数据描述符的 alternate-next 指向它。停止描述符也追加到普通链末尾，沿用既有缓存刷新和回收路径；扫描器识别并跳过它，不将它视为数据 STALL。分配失败时回收尚未交给 DMA 的整条链并返回 NOMEM。单描述符 IN、bulk OUT 和控制传输状态阶段不变，仍保留 64 KiB 接收缓冲区。可选 trace 新增摘链/交付阶段 ACTIVE、HALTED 统计，并保留主动停止情况下的成功接收证据。

实际 HCD 源码的 ASan/UBSan 测试覆盖四个短包位置、零/非零短包、未被消耗的后续描述符、完整 IN/OUT、单描述符 IN、控制状态阶段、资源耗尽与回收。上一版 IAA 驱动在新的控制器短包前进断言处失败，修正后通过。这个控制器模型不等于 USB 总线实测，仍需核对新镜像的头部/PID/错误/显示节奏，并回归重连、音乐与无线功能。aiburn 工具同时修正了探测 Monitor 时吞掉最初日志的问题：readlog 保留探测日志，串口 sendcmd 用 monitor_probe_log 单独保留命令之前的证据；离线功能检查通过，没有关闭 Monitor。
